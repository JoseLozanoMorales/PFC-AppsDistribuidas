1. ordenes-proveedores-service

Gestiona proveedores y órdenes de compra. Se comunica con inventario-service para registrar las entradas de stock cuando se confirma la recepción de una orden.

Carpeta application/ — orquestación de casos de uso

Punto de conexión #1 — clase OrdenCompraService, método registrarRecepcion() (líneas 48–58).
Cuando el controller confirma la recepción de una orden, este método primero guarda la recepción en la propia base de datos (ordenCompraRepository.registrarRecepcion(...)) y luego, en el mismo método, invoca inventarioClient.registrarEntradasPorRecepcion(ordenCompraId, recepcionPorProducto, costosPorProducto, usuario) — pero inventarioClient aquí es de tipo InventarioPort (la interfaz), no la clase concreta. Si esa llamada falla, envuelve la excepción explicando que la recepción sí quedó confirmada pero el stock no se actualizó.

ProveedorService no tiene ninguna conexión externa: solo delega en ProveedorRepository.

Punto de conexión #2 (el real) — clase InventarioClient, método registrarEntradasPorRecepcion().
Usa un RestClient de Spring configurado con base-url = ${INVENTARIO_SERVICE_URL:http://localhost:8082} (propiedad en application.properties, línea 12). Construye una lista de ítems (producto_id, subtipo_id=1 "COMPRA", cantidad, costo_unitario, referencia) y ejecuta:
restClient.post().uri("/api/sp/movimiento-inventario")...
Protegido con @CircuitBreaker(name="inventario") y @Retry(name="inventario") (Resilience4j): 3 reintentos cada 500ms, ignora errores 4xx (son rechazos de negocio, no caídas), circuito se abre tras 50% de fallos en 10 llamadas. Si el circuito está abierto o se agotan los reintentos, cae en registrarEntradasPorRecepcionFallback(), que loggea el error real y lanza IllegalStateException.

Cadena completa de la conexión

OrdenCompraController.registrarRecepcion() [presentation] → OrdenCompraService.registrarRecepcion() [application] ← orquesta → InventarioPort.registrarEntradasPorRecepcion() [domain] ← abstracción (interfaz) → InventarioClient.registrarEntradasPorRecepcion() [infrastructure/client] ← HTTP POST real a inventario-service:8082 /api/sp/movimiento-inventario

Tipo de comunicación: síncrona, HTTP/REST directo, protegida con Circuit Breaker + Retry. Si inventario-service no responde, la recepción ya quedó confirmada en la BD propia — puede quedar una inconsistencia que requiere revisión manual.

2. ventas-service

Genera facturas a partir de órdenes de pedido ya confirmadas. Se comunica con inventario-service para registrar las salidas de stock (descuento por venta), pero de forma asíncrona mediante el patrón Outbox.

Carpeta application/

FacturaService.generarDesdeOrden() NO llama directamente a inventario-service — solo delega en facturaRepository.generarDesdeOrden(ordenId). La conexión con el otro microservicio queda completamente desacoplada de la creación de la factura.

Punto de conexión #1 — clase InventarioOutboxProcessor, método reintentarPendientes().
Anotado con @Scheduled(fixedDelayString = "${outbox.inventario.retry-delay-ms:15000}"): corre cada 15 segundos (independiente de cualquier petición HTTP entrante). Lee hasta 20 facturas pendientes vía outboxRepository.facturasPendientes(5, 20) y, por cada una, llama inventarioClient.registrarSalidasPorFactura(facturaId, detalle, "outbox-retry") — de nuevo, inventarioClient es de tipo InventarioPort. Si tiene éxito, marca PROCESADO; si falla, incrementa el contador de intentos (máx. 5, luego pasa a FALLIDO).

Carpeta infrastructure/

SubcarpetaClaseRol
persistence/CrdbFacturaRepositorygenerarDesdeOrden() corre en @Transactional(isolation = SERIALIZABLE): inserta encabezado + cuerpo de la factura y la fila en ventas.factura_outbox (estado PENDIENTE) en una sola transacción atómica. Este es el punto donde nace el evento que luego procesará el outbox — pero aquí todavía no hay ninguna llamada de red.
persistence/FacturaOutboxRepositoryImplementa FacturaOutboxStore: consulta pendientes, marca procesado, registra fallos — pura SQL contra ventas.factura_outbox.
config/WebConfigCORS.
client/InventarioClientImplementa InventarioPort. Única clase con la llamada HTTP real.
Punto de conexión #2 (el real) — clase InventarioClient, método registrarSalidasPorFactura().
Mismo patrón que en ordenes-proveedores: RestClient con base-url = ${INVENTARIO_SERVICE_URL:http://localhost:8082}. Arma ítems (producto_id, subtipo_id=4 "VENTA", cantidad, fecha, referencia="FAC-{id}") y ejecuta POST /api/sp/movimiento-inventario. Igual protegido con @CircuitBreaker(name="inventario") + @Retry(name="inventario"); si falla, registrarSalidasPorFacturaFallback() lanza IllegalStateException — pero esa excepción la atrapa el InventarioOutboxProcessor, no rompe nada visible al usuario.

Cadena completa de la conexión

FacturaController.generarDesdeOrden() [presentation] → FacturaService.generarDesdeOrden() [application] → CrdbFacturaRepository.generarDesdeOrden() [infrastructure/persistence] INSERT factura + INSERT factura_outbox (PENDIENTE) — misma transacción, SIN red ⋯ 15 segundos después, en un hilo aparte ⋯ InventarioOutboxProcessor.reintentarPendientes() [application] ← @Scheduled, dispara la conexión → InventarioPort.registrarSalidasPorFactura() [domain] ← abstracción → InventarioClient.registrarSalidasPorFactura() [infrastructure/client] ← HTTP POST real a inventario-service:8082 /api/sp/movimiento-inventario

Tipo de comunicación: asíncrona, patrón Outbox transaccional. Si inventario-service no responde, la factura ya está creada y consistente; el evento sigue en PENDIENTE y se reintenta solo, sin intervención manual — más robusto que el enfoque síncrono de ordenes-proveedores-service.
